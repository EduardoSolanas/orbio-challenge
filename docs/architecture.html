Mandatory core requirement · R13

RAG: retrieve knowledge before answering

Policy question→Local FAQ retrieval · top 2→Grounded model answer→Validate + display sources

The versioned FAQ ships in the image. The engine retrieves matching policies, calls the configured RAG model with those records, and validates cited IDs. Unsupported questions receive an explicit abstention. Answers preserve collected intake facts and confirmation state.

Unit, integration, Playwright, live grounding checks and mutmut coverage are required. Exact mandatory RAG contract and seed corpus.

What we build: the Python server, conversation engine, provider adapters and browser UI. Extraction, RAG, STT and TTS call operator-selected local or remote compatible servers. The app does not train models or provision model servers.

02 / Model adapters · app/providers.py

Four roles, one interface

extract(context) → Extraction
  POST LLM_BASE_URL/chat/completions
  LLM_MODEL · explicit JSON output mode

answer_knowledge(context) → answer + source IDs
  context = question + version + retrieved sources
  POST RAG_BASE_URL/chat/completions
  own model/auth or complete LLM-profile inheritance

transcribe(validated_wav_bytes) → str
  POST STT_BASE_URL/audio/transcriptions
  STT_MODEL · independent URL/auth

synthesize(saved_reply_text) → mp3_bytes
  POST TTS_BASE_URL/audio/speech
  TTS_MODEL + TTS_VOICE · independent URL/auth

The adapter owns API mapping, capacity, timeouts and bounded attempts. Transport retries and fallback are disabled; the app owns bounded attempts. The model cannot write files, confirm an intake or issue a refund.

03 / Conversation engine · app/conversation.py

What happens when the customer presses Send

StepCaller → methodWhat it guarantees
1Browser → POST /api/sessions/{id}/turnsSend request_id, expected_revision, text and input_mode.
2Route → engine.turn(id, command)Acquire session lock; load JSON; check request replay, revision and limits.
3Engine → provider.extract(context)Send accepted slots, pending clarifications, recent history and current message once.
4Engine → validation / merge functionsModel proposes facts; Python validates and merges, then resolves rejection recovery before choosing a reply. A restored review always needs a later confirmation.
5Engine → reply / summary templatesAsk for the first issue or missing slot; otherwise show review. Confirmation is a separate state transition.
6Engine → repository.save(new_session)Atomically save both messages, slots, summary, replay response and incremented revision before success.
7HTTP response → browserRender reply, retain message_id for speech, update revision and review token. Retry reuses the original request body.

We write this engine as ordinary Python with unit-tested transitions. It is not an SDK “agent” object. The model extracts facts and generates grounded policy answers; Python controls retrieval, citation validation and every accepted state change.

04 / Speech to text

Audio becomes a draft first

  1. Stop recording or choose a WAV with the paperclip; both immediately trigger one transcription request. No Transcribe button is shown.
  2. While STT is pending, all chat controls are disabled and Message is readonly; the single-flight guard rejects duplicate starts.
  3. Server bounds bytes; audio.py validates format, duration, frames and silence.
  4. Route calls provider.transcribe(bytes); returns {text}.
  5. Browser unlocks controls and displays an editable draft. Nothing has been added to the conversation.
  6. The customer presses Send. The exact same engine.turn pipeline above runs.

Speech transcription does not bypass business validation. All upload handles close on failure or cancellation. The WAV paperclip remains disabled when a text draft exists, so it cannot overwrite customer text.

05 / Text to speech

Speak an already-saved reply

  1. Text is displayed and committed before playback.
  2. Play posts {message_id} to the session speech endpoint.
  3. Engine looks up a saved assistant message; arbitrary caller text is rejected.
  4. Route calls provider.synthesize(saved_text).
  5. Return audio/mpeg with no-store; browser plays an object URL and later revokes it.

A failed playback leaves the saved text and conversation revision intact. The page discloses that the voice is AI-generated.

06 / Build sequence · strict tests first

The implementation order

  1. Schemas and validation: write failing boundary cases, implement normalization and merges, pass unit tests.
  2. Storage and engine: write failing transaction/correction/confirmation tests, implement JSON atomicity and state transitions.
  3. Server and provider: write failing HTTP integration tests, then implement routes, lifespan assembly and real request serialization through a mocked HTTP transport.
  4. Browser UI: write failing Playwright journeys against a real server and test-only fake model, then implement Send, review, confirmation, retry and resume.
  5. Voice: test invalid WAVs, editable STT drafts and actual browser playback before implementing those behaviors.
  6. Mutation gate: run mutmut-generated mutations; improve behavioral tests for survivors; independently review equivalent mutations.
  7. Delivery: green quality gates, container startup, authorized real model/voice smoke and demo video.

J01 · Complete an intake

Complete an intake: Fresh page→PART→CATEGORY→HIGH→review→Confirm details→reload completed view→New intake.

Required checkpoints: Natural missing-field prompts; exact four slots/summary/review; one local-only receipt; completed view read-only after reload; new ID/empty intake, old saved file unchanged. No provider call for dedicated confirm or GET.

J02 · Correct and recover a rejected review

Correct and recover a rejected review: Fresh→invalid5-digit order plus valid problem→correct order→CATEGORY→HIGH→implicit order conflict→retain old order→NO→CHANGE→fresh review→later confirm.

Required checkpoints: Valid problem survives invalid order; conflict hides Confirm; explicit resolution restores review; rejection clears token/summary; valid correction recovers review but never completes same turn; later confirm saves expected low urgency. Other rejection/field permutations are IT02–IT04.

J03 · Resume across refresh and restart

Resume across refresh and restart: Create partial intake→reload hits one controlled pre-handler GET503→explicit Retry resumes→stop/restart real server at SAME origin with same temp directory→reload→finish through review/confirm.

Required checkpoints: During the503, retain localStorage ID, show visible Retry, issue no replacement POST and do not overwrite saved data. Retry uses GET to the same ID and restores identical context. Restart/reload preserves history/revision; no model call on GET. API404/corruption/status permutations remain IT01/IT06; their client-only handling is not claimed covered by those Python tests.

J04 · Recover one failed text request

Recover one failed text request: Hold FULL extraction with event→check pending controls/draft→release with one recoverable failure→Retry succeeds→confirm.

Required checkpoints: One request despite rapid second click; Send/Confirm/Transcribe/New intake disabled and Message readonly while pending; failure retains exact draft and disk unchanged; Retry body/ID identical; one eventual pair/review/receipt, no duplicate success. Does not claim commit-then-lost-response semantics (IT07).

J05 · Resolve stale state from two tabs

Resolve stale state from two tabs: Two pages share one browser context/session review at r; A commits CHANGE, B submits its stale request→B conflict/refresh→explicit B Send→resolve details→confirm.

Required checkpoints: Visible409 alert, unsent draft retained, GET refresh, no automatic extraction/replay; new explicit action uses new ID/current revision. Only one final confirmation, saved state consistent; explicitly reload the other page before comparing displayed completion (no realtime push is specified). Two pages allowed within this serial journey.

J06 · Use voice successfully

Start a microphone take→Stop automatically submits STT→review/edit the transcript draft→Send (scripted FULL facts with edited order)→Play saved reply→Confirm; separately attach a PCM WAV, which also auto-transcribes.

Required checkpoints: Stop and file selection each produce one STT request without a Transcribe button; every chat button is disabled and Message is readonly while STT is held; successful text appears in the editable Message draft with input_mode transcript and no committed session change until Send; saved assistant message ID drives actual finite MP3 playback (duration>0 and progress/play event), AI-generated disclosure, confirmation succeeds. J07 · Continue when speech fails

Continue when speech fails: Valid upload hits one STT outage→type FULL→review→Play hits one TTS outage→confirm.

Required checkpoints: Both safe errors visible, failed audio never commits a turn or poisons text; typed input mode text, text reply remains usable, one normal receipt and correct provider-method ledger. Codec/file/response permutations remain IT08–IT09.

Runtime boundary

One deployable service

The boxes inside the dashed boundary are Python modules in one container. AI roles can use one shared server or independently configured local/remote servers. Only the application container is managed by this Root Compose configuration.

Target physical deployment: Compose runs separate gateway and backend-api containers. The boxes inside each container are logical modules in that service. The current application still runs as one FastAPI service; Compose and implementation contracts must be changed before this is the running system.
Allowed business calls

Gateway → Backend API

  1. POST /internal/v1/order-verifications checks order, postcode and demo code; returns a generic mismatch or short-lived session/order-bound grant.
  2. GET /internal/v1/orders/{order_number} requires that grant and returns only the fields needed to answer.
  3. GET /health is an internal readiness check; it does not read customer data.
Security boundary

Keep the model out of the API path

The model can return only the typed lookup_verified_order proposal with empty arguments. Gateway code checks intent and verification, then makes the private request. Browser traffic cannot reach the Backend API, and no model receives the verification code, postcode, grant, API credential, or arbitrary API result fields.

Initial scope is read-only: no refunds, cancellations, order changes, email, or ticket submission.

Design boundaries

What limits incoming and provider data?

JSON requests are capped before parsing at 64 KiB; provider success JSON at 1 MiB; provider error bodies at 64 KiB; TTS at 5 MiB. Audio uploads keep their distinct WAV/multipart limits. Raw reads use identity encoding; oversized authentication-error bodies remain nonretryable. No arbitrary buffered JSON or decompression.

Why only one worker?

Session locks and request deduplication are process-local. Multiple workers could lose updates to the same JSON file. Shared transactional storage and shared idempotency are prerequisites for scaling.

What survives a restart?

Saved sessions in the named volume. Audio, in-flight failed attempts and temporary files are not durable. Ordinary Compose down preserves the volume; retention is not a backup strategy.

What happens if an AI service fails?

Extraction uses bounded attempts and a total deadline; an exhausted request does not commit a turn. Transcription leaves text input available. Speech playback failure keeps the already-saved text response intact.

What is deliberately outside core?

Vector database, Redis, streaming audio, microphone format conversion, cross-session identity, public deployment and external ticket actions. The core interview retains within-session context.
